Secret Language

Every web app you'll ever attack speaks this language. Today you learn to read it.

CASE FILE 01.A

First Contact

Establish communication. Learn what a server reveals about itself.

Picture this: you knock on a stranger's door. They open it, hand you a folder of information about themselves, and close the door. They didn't have to give you anything, but you asked nicely. That's an HTTP request and response.

The browser does this thousands of times a day. You just never see it. Time to see it.

# Open Terminal on your Mac. Type this:
$ curl https://httpbin.org/get

Run it. Look at the output. Don't worry about understanding everything — just look.

What you saw is a response. The server (httpbin.org) is an honest one — it tells you exactly what it observed about your request. Here's a typical response, annotated:

{
  "args": {},
  "headers": {
    "Accept": "*/*",
    "Host": "httpbin.org",
    "User-Agent": "curl/8.4.0"
  },
  "origin": "73.123.45.67",
  "url": "https://httpbin.org/get"
}
Notice the server saw YOUR public IP address (the origin field). It also saw that "curl" knocked on its door, not a normal browser.

The Witness Analogy. Every server is a witness. When you make a request, you leave fingerprints: your IP, your software ("User-Agent"), the language you speak, what you accept. A server can refuse to talk to you, lie to you, or report you — all based on what you reveal in your request. You are never anonymous on the web.

The User-Agent header is one of the first things attackers change. A site may block curl but accept Chrome. Switch the User-Agent → bypass the block. You'll do this on Day 7 in Burp Suite.

CASE FILE 01.B

Hidden Messages

Pass secret information to the server through the URL itself.

The URL isn't just an address. It can carry messages. Watch:

$ curl "https://httpbin.org/get?name=bhargav&role=student"

The part after ? is called a query string. It carries data to the server. Parameters are written as key=value, separated by &.

The quotes are critical: your shell (Bash/Zsh) sees & as "run in the background." Without quotes, your command breaks. Always quote URLs that contain special characters.

{
  "args": {
    "name": "bhargav",
    "role": "student"
  },
  ...
}
The server parsed your input and echoed it back. Every query parameter is user-controllable input. Remember this. It's the most important sentence in this entire document.

The Note Under The Door. Think of ?key=value as slipping a note under the door before knocking. The server reads your note, then decides how to respond. If the server trusts the note blindly... what could you write to manipulate it?

This is where SQL injection lives. Imagine ?user=admin. What if you sent ?user=admin' OR '1'='1? On Day 8, you'll do exactly this and watch a login bypass happen. The principle starts right here.

Try changing the values yourself. What happens with weird inputs?

CASE FILE 01.C

The Sealed Envelope

Send sensitive data without putting it in the URL.

What if you have to send a password? Putting it in the URL is bad — URLs end up in browser history, server logs, proxy caches, and screenshots. The fix: send data in the request body, hidden from the URL.

This is a POST request. GET asks. POST submits.

$ curl -X POST -d "username=admin&password=test123" \
    https://httpbin.org/post
ASPECT GET POST
Data lives where? In the URL In the body (hidden)
Use for? Reading data Creating, changing, submitting
Cached? Yes (by browsers) No
Length limit? ~2000 chars Effectively unlimited
In server logs? URL is logged Body usually not
When you log into any site (Gmail, your bank, Instagram), your username and password go in a POST body — never the URL. This is the same pattern.

The Postcard vs The Envelope.
GET = a postcard. Anyone in the mail chain can read it. Use for stuff you don't mind people seeing.
POST = a sealed envelope. Mostly private. Use for secrets, passwords, anything that changes things.
Sending a password by postcard? That's the same vibe as putting it in a URL.

On Day 11 you'll attack login forms. Every login uses POST. You'll change the body to bypass authentication. The skill starts here — knowing the body exists and is manipulable.

CASE FILE 01.D

The Full Confession

See the complete HTTP conversation — every byte sent, every byte received.

Time to look behind the curtain. The -v flag stands for "verbose" — curl will show you literally everything that happens.

$ curl -v https://httpbin.org/get
* Trying 54.196.x.x:443...
* Connected to httpbin.org port 443
* TLS handshake (HTTPS encryption)

> GET /get HTTP/2 ← YOUR REQUEST starts here
> Host: httpbin.org
> User-Agent: curl/8.4.0
> Accept: */*

< HTTP/2 200 ← THEIR RESPONSE starts here
< server: gunicorn/19.9.0
< content-type: application/json

{
  ...response body...
}
Lines starting with > = YOU sent that. Lines starting with < = SERVER sent that back. This is HTTP, exposed.

The Interview Transcript. Imagine HTTP as a transcript between two people: you (>) and the server (<). They take turns speaking. Headers are like the credentials each person flashes before talking. The body is what they actually say.

When you debug ANY web problem in the future, the first question is always: "Show me the request and the response." That's what -v reveals.

See that server: gunicorn/19.9.0 header? That's a vulnerability already. The server is announcing its exact software version. Attackers Google "gunicorn 19.9.0 CVE" and find known exploits. This is called information disclosure, OWASP A05. You'll find these in real apps on Day 10.

The Status Code Vault

Every response carries a 3-digit verdict. Interviewers will test you on these. Don't memorize — visualize.

200
OK
✅
"Yes, here you go."
Like ordering a coffee and getting your coffee. The default success.
201
CREATED
📦
"Made the thing you asked for."
You submitted a form to create an account. Account exists now. 201.
301
MOVED
↪️
"It's permanently at a new address."
Old URL is dead. Use the new one. Search engines update.
302
FOUND
↩️
"Go here for now."
Temporary redirect. Used after login to send you to dashboard.
400
BAD REQUEST
🤷
"I can't even understand what you're asking."
Your fault. Malformed input. Missing required field.
401
UNAUTHORIZED
🚪
"Who ARE you? Show ID."
The bouncer's first question. You haven't proven who you are.
403
FORBIDDEN
🚫
"I know who you are. You're not allowed in."
The bouncer's second answer. ID checked. You're not on the list. Different from 401.
404
NOT FOUND
👻
"That page doesn't exist here."
The famous one. Wrong URL, deleted page, or hidden resource.
429
TOO MANY
🛑
"Slow down. You're hammering me."
Rate limit hit. The server is protecting itself. Common in brute-force defenses.
500
SERVER ERROR
🔥
"I broke. Not your fault."
Their bug. AppSec gold — server errors leak stack traces and code paths.
502
BAD GATEWAY
📡
"My upstream friend isn't responding."
Server's server is down. Common in microservice meltdowns.
503
UNAVAILABLE
⏰
"Service is temporarily down."
Maintenance, overload, or temporary failure. Try later.
