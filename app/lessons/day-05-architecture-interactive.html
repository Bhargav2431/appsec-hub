Web Application
Architecture

Every app you'll ever attack has the same load-bearing structure. Learn the blueprint once, and you can read any building.

SCOPE: 3-tier model EST. TIME: 60–90 min PREREQ: Days 1–4
01
THE THREE TIERS

Open any web app — a bank, a social network, a shopping site — and you'll find the same three load-bearing floors underneath, no matter how different the paint job looks.

CROSS-SECTION VIEWTAP A FLOOR
What it controls: Everything the user sees and clicks. Forms, buttons, layout, client-side validation.

The security catch: The user fully controls this layer — they can view source, modify JavaScript, disable validation, or send requests that didn't come from your actual UI at all (curl, Burp Repeater). Anything enforced only here is not enforced at all.
USER-CONTROLLEDNEVER TRUST
What it controls: The actual logic — checking passwords, deciding who can see what, talking to the database, processing payments.

Why this is where bugs live: This is the layer that's supposed to enforce every rule the frontend only suggested. SQL injection, broken authentication, IDOR, CSRF — almost everything in the OWASP Top 10 is a backend failing to re-verify something it assumed the frontend already checked.
YOU CONTROL THISMUST VALIDATE
What it controls: Long-term storage. User accounts, transactions, content — anything that needs to survive a server restart.

Why it matters for security: This is the prize at the end of most attacks. SQL injection exists specifically to manipulate this layer through the backend. Weak encryption here means a single breach exposes everything permanently.
PERSISTENTTHE TARGET
▸ APPSEC RELEVANCE

When you audit an app, map each tier separately in your head. Frontend bugs affect the UI only. Backend bugs affect data and logic — the dangerous ones. Database bugs affect persistence. SQL injection specifically happens when the backend passes user input from the frontend tier directly into a query on the database tier — a tier-boundary failure where untrusted input crosses into a trusted execution context.

02
AUTHENTICATION VS AUTHORIZATION

These two words get used interchangeably in casual conversation, and that confusion is the root of one of the most common vulnerability classes in the OWASP Top 10. Keep them permanently separate in your head.

AUTHENTICATION
Who are you?
"Prove your identity."
Login form. Password. MFA code. Your hotel key card proving you're a guest.
AUTHORIZATION
What can you do?
"Prove your permission."
Admin vs regular user. Which rooms your specific key card actually opens.
MEMORY HOOK

The Hotel Analogy. Authentication = your key card proves who you are. Authorization = which rooms that key card actually opens. Being a guest (authenticated) doesn't get you into the penthouse (authorized). An IDOR vulnerability is like a hotel key card that opens every room because the door lock only checks "is this a valid key?" — never "is this YOUR key?" That's a backend that authenticated you correctly but forgot to authorize you for the specific resource you're requesting.

03
HOW A SESSION ACTUALLY WORKS

You'll see this exact flow referenced constantly from here through Day 60. Know it cold — not just the words, but the actual sequence of network events.

1
User submits login form: POST /login {username: admin, password: ●●●●●●●}
2
Server validates credentials, then creates a session record: session["a8f7d3"] = "admin"
3
Server responds with: Set-Cookie: session=a8f7d3; HttpOnly; Secure; SameSite=Strict
4
Browser stores this cookie — invisibly attached to every future request to this domain
5
Every subsequent request automatically includes: Cookie: session=a8f7d3
6
Server looks up a8f7d3 in its session store → knows this request is from admin
7
Session expires after a timeout, or is destroyed immediately on logout
▸ TAP A FLAG TO SEE WHAT IT BLOCKS
Set-Cookie: session=a8f7d3c9e2; HttpOnly; Secure; SameSite=Strict
HttpOnly — JavaScript cannot read this cookie via document.cookie. This is the single most important defense against session theft via XSS: even if an attacker successfully injects a script into the page, that script still can't read the session cookie to steal it.
Secure — The cookie is only ever sent over an HTTPS connection, never plain HTTP. Without this flag, anyone on the same network (coffee shop WiFi, a compromised router) could intercept the cookie in cleartext.
SameSite=Strict — The browser will not attach this cookie to requests originating from a different site. This is the primary defense against CSRF: a malicious page on evil.com cannot trigger a request to your bank that carries your real session cookie along with it.
▸ ATTACK SURFACE

Missing any one of these three flags is an automatic finding in a security assessment. No exceptions, no "it depends" — a session cookie without all three is incomplete by default, not a judgment call.
